# System and Scientific Limitations: EEFN

**Author**: Senior Research Team  
**Status**: For Journal Submission and Review  
**Objective**: Intellectual honesty regarding the limitations, boundaries, and assumptions of the Exoplanet Evidence Fusion Network (EEFN).

---

## 1. Scientific & Machine Learning Limitations

### 1. Target Label Leakage (Circular Reasoning) -- Measured (UPGRADE_PLAN.md E.1)
*   **Description**: The target validation labels (`tfopwg_disp` mapping to `CP`/`KP` or `FP`/`FA`) are derived from curation campaigns conducted by human astronomers, who retrospectively used Gaia DR3 distances and RUWE parameters to classify candidates.
*   **Impact**: Risk of feature-to-label circularity -- the model could be predicting *human categorization behavior* using Gaia-derived features (`RUWE`, `Dist`, `Rad`) rather than confirming the physical presence of a planet from independent evidence.
*   **Ablation 1 -- pre-Gaia-EDR3 subset** (`validation/scripts/leakage_ablation.py`, `backend/app/ml/leakage_ablation_report.json`): compared held-out RF performance on the full dataset (n=2667, accuracy 0.8502, ROC-AUC 0.9237) against the subset of TOIs whose `toi_created` timestamp predates the Gaia EDR3 release of 2020-12-03 (n=1527, accuracy 0.8660, ROC-AUC 0.9399) and the post-EDR3 subset (n=1140, accuracy 0.8640, ROC-AUC 0.9156). **Finding, reported without adjustment**: the pre-EDR3 subset performed *slightly better*, not worse -- the opposite of what the leakage hypothesis alone would predict. This does not rule out leakage (the dataset's `tfopwg_disp` reflects each TOI's *current* disposition, which may have been revised after Gaia EDR3 for targets created earlier, and the two subsets differ in composition for reasons unrelated to Gaia availability), but it does mean this specific ablation did not surface the expected signature.
*   **Ablation 2 -- RV-mass-confirmed clean holdout** (`validation/scripts/leakage_rv_confirmed_holdout.py`, `backend/app/ml/leakage_rv_confirmed_report.json`): cross-referenced our 2667 candidates against the NASA Exoplanet Archive's confirmed-planet table (`ps`) for radial-velocity-discovered planets -- ground truth entirely independent of TESS/TFOP/Gaia vetting. 103 candidates matched. A model trained with these 103 rows **excluded entirely** correctly flagged **93.2%** of them as positive on data it never trained on (mean predicted probability 0.768); the production-methodology model (trained on the full dataset, including these rows) reaches 100% recall on the same rows, as expected for in-sample data. The ~7-point gap between a true holdout and in-sample recall is consistent with a model that has learned real, generalizable signal beyond memorizing labels, though this checks recall on confirmed positives only -- it cannot measure false-positive rate on this specific clean-label set, since RV confirmation doesn't produce independently-verified negative examples the same way.
*   **Honest summary**: neither ablation found evidence that the model's stated accuracy is primarily an artifact of label circularity, but neither is a complete resolution of the concern -- the pre-EDR3 split is a weak proxy (see caveat above) and the RV-confirmed holdout only tests recall on positives. Both reports and their full methodology/caveats are committed alongside `model_metrics.json`; re-run both scripts whenever the training dataset changes.
*   **Future Work**: A negative-side clean-label test (e.g., candidates independently ruled out by ground-based photometry or spectroscopy, not just Gaia RUWE) would close the remaining gap; not attempted here.

### 2. Physical Simplification in Parameter Calculations
*   **Description**: Planetary equilibrium temperature ($T_{\text{eq}}$) calculations assume a fixed Bond Albedo ($A_B = 0$) and perfect uniform heat redistribution.
*   **Impact**: Calculated temperatures represent an upper blackbody limit rather than physical surface or atmospheric temperatures. This distorts the classification boundary for habitable candidates.
*   **Mitigation**: Document all $T_{\text{eq}}$ outputs as the $A_B = 0$ limit.
*   **Future Work**: Incorporate variable albedo models based on candidate size classes (e.g., $A_B = 0.3$ for gas giants) and model atmospheric circulation efficiency.

### 3. Model Architecture Constraints (Random Forest Baseline)
*   **Description**: The machine learning model relies on a baseline Random Forest Classifier. Missing stellar values (e.g., missing Gaia temperatures) are handled using a standard median imputer.
*   **Impact**: Simple median imputation distorts the natural physical distribution of stellar properties (e.g., creating artificial clusters at the median values). The Random Forest model cannot naturally model continuous physical gradients as effectively as advanced regression methods.
*   **Mitigation**: Restrict training to targets with high completeness scores.
*   **Future Work**: Implement a physics-informed imputer (e.g., using stellar track models to fill missing parameters) and evaluate Gradient Boosted Decision Trees (XGBoost/LightGBM).

### 4. Transit-Derived Stellar Density Assumes a Central Transit (b=0)
*   **Description**: `app/science/density.py::compute_transit_density_cgs` derives stellar density from transit period and duration alone (Seager & Mallen-Ornelas 2003), which requires assuming a central transit (impact parameter b=0) since the pipeline does not fit for b.
*   **Impact**: A nonzero impact parameter inflates the observed transit duration relative to the central-transit case, biasing the derived density low. Validated against TRAPPIST-1b (real b~0.13): the formula reads ~24% low against the star's actual density. `density_discrepancy_sigma`'s radius-uncertainty term is real (propagated from Gaia DR3 FLAME `b_Rad`/`B_Rad` when available), but stellar mass error and transit-timing error are not yet propagated per-target (the NASA TAP query does not currently fetch `pl_orbpererr*`/`pl_trandurherr*`) and are instead covered by a disclosed fixed floor (`UNMODELED_SYSTEMATIC_FRACTIONAL_FLOOR = 0.10`).
*   **Mitigation**: Both simplifications are named constants with docstrings pointing here, not silent assumptions; `density_discrepancy_sigma` is a real per-target value that varies with measurement quality, not a fixed divisor.
*   **Future Work**: Fetch impact-parameter/inclination and its error columns to remove the b=0 assumption; fetch `pl_orbpererr*`/`pl_trandurherr*`/Gaia FLAME mass error columns to fully propagate `density_transit`'s and `density_gaia`'s uncertainty instead of relying on the systematic floor.

### 5. Missing-Data Masking for the DL Metadata Vector -- Done (RF path was already fine)
*   **Description**: The DL centroid branch carries an explicit presence mask (`app/ml/deep_learning_pipeline.py::build_centroid_matrix`) instead of treating an all-zero array as a real flat measurement (UPGRADE_PLAN.md A.6). As of the F.2 pass below, every optional-catalog-derived field in the DL metadata vector -- not just RUWE -- carries its own presence bit. The Random Forest path (`predict.py::build_feature_row`) leaves genuinely missing inputs as `None`/NaN for its trained median `SimpleImputer` and never needed this fix.
*   **F.1/F.2/F.5 status (2026-08-11 update)**: `app/science/tiers.py` reports which of the 7 catalogs actually backed a candidate (F.1) -- built to check real per-catalog DB provenance rather than raw field non-nullness, specifically because `backend/seed_db.py` fabricates demo values for `centroid_shift_max`/`teff_spec`/`fe_h` and a naive field-presence check would have reported those as real catalog coverage (a real bug, found and fixed while building this). 2MASS and Pan-STARRS are live in `ingest.py` (F.5, 3/7 -> 5/7 catalogs; verified against real CDS X-Match responses), with full `MeasurementHistory` provenance. The DL metadata vector (F.2) was expanded from 16 to 28 dimensions (`DL_ARCHITECTURE_VERSION` bumped to `...28feat...3`, retrained on the current DB's real candidates -- 101 candidates, 1252 augmented samples, 99.5% synthetic-train accuracy, checkpoint verified to load with `model_status="trained"`): added `h_mag` (2MASS) and `g_mag`/`r_mag` (Pan-STARRS, 2 of 5 bands -- chosen as most broadly available rather than all five, to keep the vector's width reasonable for a still-synthetic-only training set), plus 10 presence bits covering every optional field (`ruwe_present`, `st_teff_present`, `st_rad_present`, `st_dist_present`, `j_mag_present`, `k_mag_present`, `h_mag_present`, `fe_h_present`, `g_mag_present`, `r_mag_present`).
*   **Impact**: A candidate missing 2MASS/Pan-STARRS/stellar-parameter data now presents that as an explicit 0.0 presence bit to the network, not indistinguishable from a real measurement at the default value.
*   **Still not done**: the RF feature vector doesn't consume 2MASS/Pan-STARRS at all -- that needs `validation/data/validation_dataset.csv` augmented with those columns (a real cross-match against the training set) and a full RF retrain, deliberately not attempted in the same pass as the DL change. `i_mag`/`z_mag`/`y_mag` (the other 3 Pan-STARRS bands) and `alpha_fe` are still unused by either model.
*   **Mitigation**: `completeness` remains a real, non-fabricated per-target value (fraction of core fields actually populated) as an aggregate signal alongside the new per-field bits.
*   **Future Work**: Augment `validation_dataset.csv` with 2MASS/Pan-STARRS columns and retrain the RF to close the remaining gap.

### 6. Random Forest Calibration -- Measured (UPGRADE_PLAN.md E.2)
*   **Description**: `evidence_consistency_score` is a probability; a stated "84% consistent" is only meaningful if things predicted at 84% actually turn out positive ~84% of the time. Before this, calibration had never been measured -- only accuracy/ROC-AUC/F1.
*   **Findings**: `validation/scripts/train_and_serialize_model.py` now computes a 10-bin reliability diagram and Brier score (`backend/app/ml/calibration_report.json`, served via `GET /api/v1/predictions/calibration`) on the same held-out test split as `model_metrics.json`. Latest run: **Brier score 0.1127** (0=perfect, 0.25=uninformative constant-0.5 baseline, 1=worst) on 534 held-out samples. The model is reasonably well-calibrated at the extremes (e.g. predicted ~0.94 -> observed 0.972; predicted ~0.85 -> observed 0.868) but measurably overconfident in the low-to-mid range (predicted ~0.24 -> observed 0.128; predicted ~0.35 -> observed 0.229) -- roughly a real, disclosed gap of the kind this document exists to surface, not an unexamined "well-calibrated" claim.
*   **Impact**: Anyone triaging on `evidence_consistency_score` alone in the 0.2-0.4 range should treat it as a modest overestimate; the top and bottom deciles are the most trustworthy.
*   **Deep-learning temperature scaling -- explicitly deferred, not done**: `DeepExoFusionNet`'s fixed `temperature=1.15` (`deep_learning_pipeline.py`) is still an unvalidated constant, not empirically fit. Fitting it now would only be possible against the model's synthetic training/validation data (see item 7 below) -- a temperature fit to calibrate synthetic-light-curve confidence has no established relationship to calibration on real light curves, so doing that exercise now would risk manufacturing false confidence in a number that looks validated but isn't meaningfully so. Deferred to when F.6 (real MAST light curves) lands.
*   **Future Work**: Re-run calibration whenever the RF model is retrained (dataset growth, feature changes); revisit DL temperature scaling once real training data exists (F.6).

### 7. Deep Learning Model (ExoFusion-Net v2) -- Retrained on Real Data (2026-08-21), Small Sample, Real Overfitting
*   **Description**: `DeepExoFusionNet` was previously trained entirely on synthetic light curves. It has now been retrained on **116 real Kepler stars** (`validation/scripts/fetch_real_kepler_dataset.py`) with real disposition + false-positive-reason labels from the NASA Exoplanet Archive's cumulative KOI table -- the same source Shallue & Vanderburg (2018) used. No synthetic light curve appears anywhere in this training set. The output space was honestly reduced from 4 classes to 3 (`Planet Transit` / `Eclipsing Binary` / `Not Transit-Like`) because no standard dataset -- Kepler's own vetting flags included -- separates "stellar activity" from "instrumental noise" at the per-example level; keeping a 4th class would have meant it stayed synthetic-only while the other three became real.
*   **Real, measured result** (`app/ml/dl_training_report.json`, held out at the *star* level so no augmented copy of a training star leaks into the test set): **60.9% accuracy on 92 held-out real samples** (23 real stars never trained on), against **100% training accuracy** -- a clear, expected overfitting signature for a 3.86M-parameter network trained on only 93 real training stars. Per-class held-out accuracy: Not Transit-Like 100% (32/32), Planet Transit 50% (12/24), Eclipsing Binary 33% (12/36, no better than chance). The model currently cannot reliably distinguish a real planet transit from a real eclipsing binary; it can reliably tell a non-detection from either.
*   **Impact**: This is a real, honestly-measured, modest result -- not a validated classifier, but also no longer a demonstration running on fabricated data. Read `dl_classification` accordingly: trust "Not Transit-Like" calls far more than a "Planet Transit" vs "Eclipsing Binary" distinction today. The centroid branch still has never seen a real photocentre measurement for these Kepler stars (honestly zeroed/presence=0, not fabricated) and the metadata vector uses only real `koi_steff`/`koi_srad`/`koi_depth` -- no 2MASS/Pan-STARRS/RUWE cross-match was attempted for Kepler stars in this pass.
*   **Mitigation**: Every API response from `vet_candidate()` still includes `model_status`, `degraded`, and `centroid_available`. `GET /api/v1/predictions/dl_training` serves the real training report (503 if missing, never a fallback number) and the `/ai-analysis` page renders it directly rather than the hardcoded stale statistics it previously showed.
*   **Future Work**: More real stars (116 is small for this architecture -- several hundred per class would meaningfully close the train/test gap), real TPF-derived centroid offsets for Kepler or TESS stars (F.6), and a real 2MASS/Pan-STARRS/Gaia cross-match for the Kepler metadata vector.

### 8. Real MAST Centroid and Spectroscopy Ingestion -- Built, Verified, Deliberately Subset-Scoped (UPGRADE_PLAN.md F.6/F.7)
*   **Description**: `app/pipeline/mast_centroid.py` downloads a real TESS target-pixel-file via `lightkurve`/`astroquery.mast`, computes a real intensity-weighted photocentre per cadence, and compares the mean in-transit vs. out-of-transit position -- the classic background-eclipsing-binary signature. `app/pipeline/spectroscopy.py` performs a real VizieR cone-search cross-match against APOGEE-2 DR17 (catalog `III/286`). Both are genuine, network-verified, non-synthetic measurements (`ExoplanetCandidate.centroid_is_real` / `HostStar.spectroscopy_is_real` distinguish them from `seed_db.py`'s fabricated demo values of the same fields).
*   **Verified run (centroid, 2026-08-12)**: `validation/scripts/run_real_centroid_subset.py` against 5 real candidates -- all 5 produced a real measurement (see `backend/app/ml/centroid_subset_report.json`). Notably, **TOI-104.01 measured a 5.43-sigma in-transit/out-of-transit centroid offset** (0.114" at TESS's ~21"/pixel scale) -- a genuine, real-data signal worth a human look, not a demonstration artifact.
*   **Verified run (spectroscopy, 2026-08-12)**: `validation/scripts/run_real_spectroscopy_subset.py` -- see `backend/app/ml/spectroscopy_subset_report.json` for the actual match count. APOGEE-2 is a targeted, not all-sky, survey, so a low match rate is the correct and expected outcome, not a bug.
*   **Impact**: Both pipelines are real and working, but deliberately not run against the full ~7,000-candidate catalog in this pass -- TPF downloads are GB-scale per target and need their own caching/storage design before that's appropriate (the plan's own framing: "treat it as its own milestone, not a quick add"). `tiers.py`'s `has_real_centroid`/`has_real_spectroscopy` flags are wired to these real DB columns end to end, so Tier 3 becomes reachable exactly for the candidates these scripts have actually processed, and only those. The real per-cadence photocentre offsets are also phase-folded into the same 201-bin local-view window `CentroidSpatialCNN` was trained on (`ExoplanetCandidate.centroid_dx_json`/`centroid_dy_json`) and wired into `/transit_pipeline`'s `stellar_params` -- verified live: TOI-104.01 (the 5.43-sigma candidate above) now returns `dl_centroid_available: true`, a real measurement genuinely reaching the network, not just the health/alert layer.
*   **Caveat**: the network has still only ever been trained on the synthetic centroid proxy (`_synthetic_centroid`, arbitrary units chosen to roughly resemble real arcsec-scale offsets) -- feeding it a real arcsec-scaled measurement closes the plumbing gap but does not mean the network's *classification* of that input has been validated; treat `dl_classification` on a real-centroid candidate with the same synthetic-training caveat as item 7 above, not as newly trustworthy just because the input is now real.
*   **Future Work**: Design a caching/storage layer (local TPF cache, incremental sector coverage) and run both scripts at meaningfully larger scale; consider a background job (D.2's Arq worker) for a nightly incremental subset rather than a manual script.

## 2. Catalog & API Dependencies

### 1. Schema Dependency on Gaia DR3
*   **Description**: The database schemas, model feature pipelines, and VizieR coordinate queries are hardcoded to the Gaia DR3 column definitions and tables.
*   **Impact**: High fragility to future catalog releases. The upcoming release of **Gaia DR4** (changing table structures and astrophysical parameter pipelines) will break the ingestion pipeline, rendering the automated queries obsolete.
*   **Mitigation**: Limit Gaia query structures to essential astrometric vectors (RA, Dec, parallax, proper motions).
*   **Future Work**: Implement a dynamic catalog abstraction layer that maps incoming features to database structures regardless of release version.

### 2. External API Rate-Limiting -- Mitigated (UPGRADE_PLAN.md D.2)
*   **Description**: The ingestion pipeline makes direct HTTP queries to public astronomy data servers (CDS Strasbourg, VizieR, and MAST).
*   **Status**: A Redis-backed, cross-process token-bucket rate limiter (`backend/app/pipeline/rate_limiter.py`, default 2 requests/second, shared across every Arq worker process via `settings.CATALOG_RATE_LIMIT_PER_SECOND`) is now applied to every NASA TAP GET and every CDS X-Match POST call in `ingest.py`, including retries. This was previously a documented-but-unimplemented risk; it is now real and unit-tested (`tests/test_rate_limiter.py`).
*   **Remaining gap**: The limit is a single global budget, not yet per-catalog (a burst of NASA TAP calls and a burst of CDS calls currently share one bucket) -- acceptable at current scale, worth splitting if catalog count/throughput grows materially (ties to F.5-F.7 adding more catalogs).
*   **Future Work**: Host a local cache database containing TESS and Gaia parameters for flagship sectors to reduce public web query volume further; consider per-catalog buckets if F.5-F.7 catalog volume warrants it.

## 3. Operational & Engineering Limitations

### 1. Standalone Portal Adoption Barrier
*   **Description**: EEFN is designed as a standalone Next.js web application, which requires telescope allocators and schedulers to log into a separate dashboard.
*   **Impact**: Astronomers already suffer from portal fatigue. Standalone deployment prevents actual integration into observer scheduling routines; observers will continue to use ExoFOP and MAST as their single sources of truth.
*   **Mitigation**: Expose all alert flags and ML prediction scores via structured REST API endpoints.
*   **Future Work**: Build integration webhook libraries to export EEFN alert flags directly into ExoFOP-TESS tables.

### 2. Single-Node Database Concurrency -- Mitigated for the primary case (UPGRADE_PLAN.md D.1)
*   **Description**: The backend previously only supported a single local SQLite database file (`eefn.db`), which enforces database-level write locks under concurrent writers.
*   **Status**: Postgres is now a fully supported target (`docker-compose.yml`'s `postgres` service; dialect-agnostic `sqlalchemy.Uuid` columns; Alembic migrations verified against both SQLite and a real Postgres container) -- deploying against Postgres removes the SQLite single-writer constraint. SQLite remains supported for local single-developer use, where the constraint doesn't matter.
*   **Remaining gap**: `DATABASE_URL` must actually be pointed at Postgres for a multi-writer deployment; SQLite is still the default in `app/config.py` for zero-setup local dev, so a deployment that doesn't override this env var would still hit the original limitation.
*   **Future Work**: Document the Postgres `DATABASE_URL` requirement prominently for any non-single-developer deployment (README/deployment guide).

### 3. Idealized Impact Study Assumptions
*   **Description**: The historical impact analysis assumes that ground-based observatories would have allocated expensive observing hours to all false positives blindly.
*   **Impact**: Cost and telescope hours saved are highly idealized and overclaimed. Astronomers manually vet targets using simple filters (e.g., dropping targets with high Gaia RUWE values) before scheduling, meaning actual operational savings are significantly lower.
*   **Mitigation**: Adjust cost-saving statistics to evaluate savings relative to a baseline manual-vetting model rather than a zero-vetting baseline.
*   **Future Work**: Interview observatory scheduling managers to establish realistic baseline allocation strategies.

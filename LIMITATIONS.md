## 1. Scientific & Machine Learning Limitations

### 1. Target Label Leakage (Circular Reasoning) -- Measured (UPGRADE_PLAN.md E.1)
*   **Description**: The target validation labels (`tfopwg_disp` mapping to `CP`/`KP` or `FP`/`FA`) are derived from curation campaigns conducted by human astronomers, who retrospectively used Gaia DR3 distances and RUWE parameters to classify candidates.
*   **Impact**: Risk of feature-to-label circularity -- the model could be predicting *human categorization behavior* using Gaia-derived features (`RUWE`, `Dist`, `Rad`) rather than confirming the physical presence of a planet from independent evidence.
*   **Ablation 1 -- pre-Gaia-EDR3 subset** (`validation/scripts/leakage_ablation.py`, `backend/app/ml/leakage_ablation_report.json`): compared held-out RF performance on the full dataset (n=2667, accuracy 0.8502, ROC-AUC 0.9282) against the subset of TOIs whose `toi_created` timestamp predates the Gaia EDR3 release of 2020-12-03 (n=1527, accuracy 0.8660, ROC-AUC 0.9418) and the post-EDR3 subset (n=1140, accuracy 0.8465, ROC-AUC 0.9074; refreshed 2026-10-11 on the current feature set -- the probe itself still uses a Random Forest, independent of the production model). **Finding, reported without adjustment**: the pre-EDR3 subset performed *slightly better*, not worse -- the opposite of what the leakage hypothesis alone would predict. This does not rule out leakage (the dataset's `tfopwg_disp` reflects each TOI's *current* disposition, which may have been revised after Gaia EDR3 for targets created earlier, and the two subsets differ in composition for reasons unrelated to Gaia availability), but it does mean this specific ablation did not surface the expected signature.
*   **Ablation 2 -- RV-mass-confirmed clean holdout** (`validation/scripts/leakage_rv_confirmed_holdout.py`, `backend/app/ml/leakage_rv_confirmed_report.json`): cross-referenced our 2667 candidates against the NASA Exoplanet Archive's confirmed-planet table (`ps`) for radial-velocity-discovered planets -- ground truth entirely independent of TESS/TFOP/Gaia vetting. 104 candidates matched. A model trained with these 104 rows **excluded entirely** correctly flagged **91.4%** of them as positive on data it never trained on (mean predicted probability 0.764; refreshed 2026-10-11); the production-methodology model (trained on the full dataset, including these rows) reaches 100% recall on the same rows, as expected for in-sample data. The ~9-point gap between a true holdout and in-sample recall is consistent with a model that has learned real, generalizable signal beyond memorizing labels, though this checks recall on confirmed positives only -- it cannot measure false-positive rate on this specific clean-label set, since RV confirmation doesn't produce independently-verified negative examples the same way.
*   **Honest summary**: neither ablation found evidence that the model's stated accuracy is primarily an artifact of label circularity, but neither is a complete resolution of the concern -- the pre-EDR3 split is a weak proxy (see caveat above) and the RV-confirmed holdout only tests recall on positives. Both reports and their full methodology/caveats are committed alongside `model_metrics.json`; re-run both scripts whenever the training dataset changes.
*   **Future Work**: A negative-side clean-label test (e.g., candidates independently ruled out by ground-based photometry or spectroscopy, not just Gaia RUWE) would close the remaining gap; not attempted here.

### 2. Physical Simplification in Parameter Calculations
*   **Description**: Planetary equilibrium temperature ($T_{\text{eq}}$) calculations assume a fixed Bond Albedo ($A_B = 0$) and perfect uniform heat redistribution.
*   **Impact**: Calculated temperatures represent an upper blackbody limit rather than physical surface or atmospheric temperatures. This distorts the classification boundary for habitable candidates.
*   **Mitigation**: Document all $T_{\text{eq}}$ outputs as the $A_B = 0$ limit.
*   **Future Work**: Incorporate variable albedo models based on candidate size classes (e.g., $A_B = 0.3$ for gas giants) and model atmospheric circulation efficiency.

### 3. Evidence-Consistency Model -- LightGBM, Compared Against the Random Forest (2026-10-11)
*   **Description**: `evidence_consistency_score` now comes from a LightGBM gradient-boosted model (`validation/scripts/train_and_serialize_model.py`, `backend/app/ml/predict.py`), replacing the Random Forest. Selected by repeated stratified 5-fold CV (6 repeats, 2,667 labelled TOIs): Random Forest accuracy 0.848 / ROC-AUC 0.920 / Brier 0.114 vs LightGBM 0.854 / 0.928 / 0.104 on the same features. Held-out split of the shipped model: accuracy 0.8539, ROC-AUC 0.9267, Brier 0.1003 (`model_metrics.json`).
*   **2MASS / Pan-STARRS features -- measured, and they did not help**: four production-computable photometric features (J-K, H-K, absolute K magnitude from the Gaia parallax, Pan-STARRS g-r) were added after cross-matching the whole training set (`validation/scripts/augment_dataset_photometry.py`: 2MASS matched 2,577/2,667, Pan-STARRS 1,718/2,667 -- Pan-STARRS covers Dec > -30 only). Cross-validated accuracy with and without them is identical to within noise (0.8535 vs 0.8535). They are kept because the data is real and costs nothing, but the gain in the table above is from the algorithm, not the photometry: the Teff/radius already in the model carry that colour information.
*   **Train/serve skew fixed**: the previous feature set included `st_tmag` and `tmag_gmag_diff`, which production could never supply (HostStar stores neither the TESS magnitude nor Gaia G), so serving silently imputed them while training saw real values. Both were removed; this cost 0.0004 of CV accuracy. Features using Gaia G colours would add ~0.7 points but need Gaia G stored per host plus a backfill; not done.
*   **A second, larger train/serve skew found by an independent audit (2026-10-13) and fixed**: training computes `teff_diff`/`rad_diff`/`dist_diff` as |TOI-table value - Gaia value|, but `HostStar` stored only the Gaia values and serving copied them into both slots, so every disagreement feature was exactly 0 for the 440 live candidates with Gaia parameters (missing for the rest). Recomputed serving-style on the held-out data this cost AUC 0.927 -> 0.900 and accuracy 0.854 -> 0.807, so the served score was materially worse than the published metrics. Fixed by storing the TOI-side values (`HostStar.toi_*`), building serving inputs from the same two sources training used (`PredictionEngine.inputs_from_records`), a backfill + re-score of the existing database (`validation/scripts/backfill_toi_stellar_params.py`), a `model_version` on every stored score, and a parity test (`tests/test_serving_parity.py`) that pushes 400 real rows through both feature builders and requires identical features. Also removed the `pl_rade or 1.0` fallback that stored the catalog's own radius (or an invented 1.0) as the "Gaia-derived" radius, making a star Gaia never characterised read as perfect agreement. **Honest evaluation (2026-10-13, `validation/scripts/honest_evaluation.py`, `honest_evaluation_report.json`, `GET /api/v1/predictions/honest_evaluation`)**: the published 0.927 AUC / 0.854 accuracy comes from one random split. Re-scored with 95% bootstrap CIs resampled by star, against a TOI-table-only baseline (the ten `pl_*`/`st_*` columns): star-grouped 5-fold CV gives AUC **0.927** (CI 0.917-0.936) vs **0.919** for the TOI-only baseline, so the Gaia/2MASS/Pan-STARRS features add **+0.008 AUC (CI +0.002 to +0.014)** -- real but small. Time-forward splits (train on TOIs created up to a cutoff, test on later ones, test stars removed from train) are the realistic protocol and are markedly worse: AUC **0.844** (train to 2020-12-31, n=1,097), **0.872** (to 2021, n=485), **0.876** (to 2022, n=224), with Brier 0.15-0.17, and the cross-catalog features add **nothing** there (gain -0.000, -0.001, -0.012; every CI includes 0). Only 105 of 2,524 stars have more than one TOI, so sibling leakage in the random split is negligible (grouped and random AUC agree). Honest description of the score: a disposition prior learned mostly from TOI-table values, ~0.93 AUC at recovering labels, ~0.85 on genuinely later candidates, not independent evidence. Its training labels are resolved dispositions only (CP/KP/FP/FA), so it is not a planet probability for the unresolved PCs it would be used on; a prospective test on those is still to be done. Candidates whose host has no Gaia astrophysical parameters (~30% of the live database once seed rows are counted) still score lower on average (0.27 vs 0.54) -- consistent with the labelled data (35% vs 53% positive when missing) but a learned missingness pattern, not evidence about the planet.
*   **Missing values**: median imputation is still used (the imputer is part of the artifact). LightGBM can take NaN natively; not switched, to keep the serialization contract unchanged.
*   **Pinned versions**: pickled models are only safe across identical library versions, so `scikit-learn==1.9.1` and `lightgbm==4.7.0` are pinned exactly; both versions are recorded in the artifact and `model_metrics.json`, and the loader warns on a mismatch.
*   **Future Work**: store Gaia G per host to recover the colour features; a physics-informed imputer.

### 4. Transit-Derived Stellar Density Assumes a Central Transit (b=0)
*   **Description**: `app/science/density.py::compute_transit_density_cgs` derives stellar density from transit period and duration alone (Seager & Mallen-Ornelas 2003), which requires assuming a central transit (impact parameter b=0) since the pipeline does not fit for b.
*   **Impact**: A nonzero impact parameter inflates the observed transit duration relative to the central-transit case, biasing the derived density low. Validated against TRAPPIST-1b (real b~0.13): the formula reads ~24% low against the star's actual density. `density_discrepancy_sigma`'s radius-uncertainty term is real (propagated from Gaia DR3 FLAME `b_Rad`/`B_Rad` when available), but stellar mass error and transit-timing error are not yet propagated per-target (the NASA TAP query does not currently fetch `pl_orbpererr*`/`pl_trandurherr*`) and are instead covered by a disclosed fixed floor (`UNMODELED_SYSTEMATIC_FRACTIONAL_FLOOR = 0.10`).
*   **Mitigation**: Both simplifications are named constants with docstrings pointing here, not silent assumptions; `density_discrepancy_sigma` is a real per-target value that varies with measurement quality, not a fixed divisor.
*   **Future Work**: Fetch impact-parameter/inclination and its error columns to remove the b=0 assumption; fetch `pl_orbpererr*`/`pl_trandurherr*`/Gaia FLAME mass error columns to fully propagate `density_transit`'s and `density_gaia`'s uncertainty instead of relying on the systematic floor.

### 5. Missing-Data Masking for the DL Metadata Vector -- Done (RF path was already fine)
*   **Description**: The DL centroid branch carries an explicit presence mask (`app/ml/deep_learning_pipeline.py::build_centroid_matrix`) instead of treating an all-zero array as a real flat measurement (UPGRADE_PLAN.md A.6). As of the F.2 pass below, every optional-catalog-derived field in the DL metadata vector -- not just RUWE -- carries its own presence bit. The Random Forest path (`predict.py::build_feature_row`) leaves genuinely missing inputs as `None`/NaN for its trained median `SimpleImputer` and never needed this fix.
*   **F.1/F.2/F.5 status (2026-08-11 update)**: `app/science/tiers.py` reports which of the 7 catalogs actually backed a candidate (F.1) -- built to check real per-catalog DB provenance rather than raw field non-nullness, specifically because `backend/seed_db.py` fabricates demo values for `centroid_shift_max`/`teff_spec`/`fe_h` and a naive field-presence check would have reported those as real catalog coverage (a real bug, found and fixed while building this). 2MASS and Pan-STARRS are live in `ingest.py` (F.5, 3/7 -> 5/7 catalogs; verified against real CDS X-Match responses), with full `MeasurementHistory` provenance. The DL metadata vector (F.2) was expanded from 16 to 28 dimensions (`DL_ARCHITECTURE_VERSION` bumped to `...28feat...3`, retrained on the current DB's real candidates -- 101 candidates, 1252 augmented samples, 99.5% synthetic-train accuracy, checkpoint verified to load with `model_status="trained"`): added `h_mag` (2MASS) and `g_mag`/`r_mag` (Pan-STARRS, 2 of 5 bands -- chosen as most broadly available rather than all five, to keep the vector's width reasonable for a still-synthetic-only training set), plus 10 presence bits covering every optional field (`ruwe_present`, `st_teff_present`, `st_rad_present`, `st_dist_present`, `j_mag_present`, `k_mag_present`, `h_mag_present`, `fe_h_present`, `g_mag_present`, `r_mag_present`).
*   **Impact**: A candidate missing 2MASS/Pan-STARRS/stellar-parameter data now presents that as an explicit 0.0 presence bit to the network, not indistinguishable from a real measurement at the default value.
*   **Still not done**: `i_mag`/`z_mag`/`y_mag` (the other 3 Pan-STARRS bands) and `alpha_fe` are unused by every model. (The tabular model now consumes 2MASS/Pan-STARRS -- see item 3 -- but measured no gain from it.)
*   **Mitigation**: `completeness` remains a real, non-fabricated per-target value (fraction of core fields actually populated) as an aggregate signal alongside the new per-field bits.

### 6. Evidence-Consistency Calibration -- Measured (UPGRADE_PLAN.md E.2), Refreshed 2026-10-11
*   **Description**: `evidence_consistency_score` is a probability; a stated "84% consistent" is only meaningful if things predicted at 84% actually turn out positive ~84% of the time. `validation/scripts/train_and_serialize_model.py` computes a 10-bin reliability diagram and Brier score (`backend/app/ml/calibration_report.json`, served via `GET /api/v1/predictions/calibration`) on the held-out split.
*   **Findings (LightGBM)**: **Brier score 0.1003** on 534 held-out samples (the Random Forest scored 0.1127). The extremes are well calibrated (predicted ~0.85 -> observed 0.853; predicted ~0.95 -> observed 0.909). The mid-range has flipped direction relative to the Random Forest: it is now mildly *under*-confident (predicted ~0.26 -> observed 0.41; predicted ~0.35 -> observed 0.46). Those bins hold only 13-25 samples each, so treat them as indicative.
*   **Impact**: Scores in the 0.2-0.5 range understate the real positive rate somewhat; the top and bottom deciles are the most trustworthy.
*   **Light-curve vetter calibration**: not calibrated -- see item 7.
*   **Future Work**: Re-run calibration whenever the model is retrained; consider isotonic/Platt recalibration once there is enough held-out data per bin.

### 7. Light-Curve Vetting Model -- The CNN Was the Wrong Architecture; Replaced (2026-10-11)
*   **What was wrong with the previous model**: `DeepExoFusionNet` (3.9M-parameter 4-branch CNN) trained on 116 real Kepler stars reported 60.9% on one 23-star split. That split was too small to mean anything. Re-evaluated with star-grouped, repeated stratified cross-validation on 205 KOIs from 169 stars (`validation/scripts/dl_architecture_study.py`, `backend/app/ml/dl_architecture_study.json`), it scores **63.9% +/- 10.4** (fold-to-fold) against a 48.8% majority-class baseline. It also could not be served honestly: `/transit_pipeline` fed it a *simulated* light curve generated from the candidate's own catalog period/depth/duration, so its output was a function of those catalog numbers, not evidence. Adding 2MASS/Pan-STARRS metadata did not rescue it.
*   **Architectures compared** (same real data, same labels, same grouped folds):

    | Model | CV accuracy | Macro-F1 |
    |---|---|---|
    | `DeepExoFusionNet` (previous production) | 0.639 +/- 0.104 | 0.588 |
    | Compact dual-view CNN (~60k params, global pooling, augmentation, 3-seed ensemble) | 0.721 +/- 0.062 | 0.723 |
    | **Gradient boosting on physics features** | **0.839 +/- 0.044** | **0.820** |
    | CNN embedding + physics features | 0.837 +/- 0.066 | 0.820 |

    With ~170 labelled stars a data-hungry network cannot learn the shape of a transit. The same information an astronomer checks by hand (odd/even depth agreement, secondary eclipse, flat vs V-shaped bottom, implied planet radius vs plausibility, duration vs expected from the stellar density) can be computed directly, leaving a model with ~20 inputs that boosted trees fit reliably. The hybrid matched it but added complexity for no gain, so the simple model ships.
*   **What ships**: `app/ml/lightcurve_features.py` (single implementation of detrending + features, used by both training and serving) and `app/ml/lightcurve_vetter.py`, trained by `validation/scripts/train_lightcurve_vetter.py`. Star-grouped CV: **82.9% +/- 5.6**, macro-F1 0.81 (`lightcurve_vetter_report.json`, `GET /api/v1/predictions/lightcurve_vetter`). Classes: Planet Transit / Eclipsing Binary / Not Transit-Like. Transit-masked detrending was added; the previous views had none.
*   **Transfer to TESS -- measured, and weaker** (`validation/scripts/tess_transfer_check.py`, `tess_transfer_report.json`): 50 real TOIs (25 TFOP planets, 25 TFOP false positives) with real SPOC 2-minute light curves, vetted by the shipped v1.1.0, gave **76% agreement** with the human label and ROC-AUC **0.81** for planet-vs-not. **The balance matters more than the headline**: it recovers 88% of TFOP planets (22/25) but calls 36% of TFOP false positives planets (9/25; non-planet recall 64%), so a "Planet Transit" verdict is weaker evidence than a "Not Transit-Like" one. For comparison, v1.0.0 scored 72% / 0.83 on the same protocol (planet recall 68%, non-planet recall 76%); with n=50 the accuracy difference is within noise, but the trade of non-planet recall for planet recall is a real consequence of the missing-data fix below. Realistic expectation on TESS: mid-70s, not the 83% Kepler figure. Causes: Kepler -> TESS domain shift (far fewer transits per target in one 27-day sector, so SNR-type features are systematically lower), and TFOP labels were assigned by humans who looked at these same light curves, so this measures reproduction of human vetting, not independent discovery. Seven of 57 attempted TOIs had no 2-minute SPOC light curve and were excluded. The check now looks up each TOI's own epoch (an earlier version could pair a TOI with a sibling planet's epoch on multi-planet stars) and skips -- without caching -- targets where the archive timed out.
*   **Honest gaps**: (1) outputs are **not calibrated** -- they are raw boosted-tree probabilities; (2) no centroid information in the model (Kepler's "Eclipsing Binary" label includes its centroid-offset flag, which the model cannot see) -- real TESS centroid offsets are a separate piece of evidence (item 8); (3) the dataset is small -- 169 stars, because MAST download throughput limited further fetching -- so the headline number carries a +/-5 point spread; (4) "Not Transit-Like" is the weakest class (recall ~0.77).
*   **Missing-data shortcut found by a post-hoc check on real candidates, and fixed (v1.1.0)**: in the Kepler training set a missing stellar radius/Teff occurred *only* for "Not Transit-Like" stars (7 of 39; 0 of 166 for the other classes), so the first model learned "no stellar radius -> Not Transit-Like". About 20% of this project's hosts (100/509) have no radius, and a known planet (TOI-104.01, SNR 127, clean odd/even, no secondary) scored **90% Not Transit-Like** purely because its radius was missing. The training pipeline now also trains every class on copies with the stellar group (and separately the photometry group) masked, so missingness carries no label; cross-validated accuracy is unchanged (82.9%) with or without the stellar inputs at test time, and TOI-104.01 now reads Planet Transit at 85%. Regression test: `tests/test_vetter_missingness.py`. Of 8 known planets re-vetted on real light curves, 6 were called planets and 2 (TOI-102.01, TOI-107.01) Eclipsing Binary -- a real error rate on a tiny sample. The 50-target TESS check above did not catch this because its input table (a CSV) almost always has a stellar radius, unlike the live database.
*   **Serving**: `/transit_pipeline` no longer classifies the simulation. A nightly sync (`app/pipeline/real_sync.py::sync_real_lightcurve_vetting`, Arq cron) vets each candidate against its real SPOC light curve and stores the result; the endpoint returns it with `dl_input_source="real_tess_spoc_2min"`, or `dl_model_status="no_real_lightcurve"` with an empty classification when none exists yet. `DeepExoFusionNet` and `train_deep_learning.py` remain in the repo as the documented baseline; they are not used for any served output.
*   **Also fixed**: the physics-veto blend in `vet_candidate` had a 4-entry prior against a 3-class output and raised a broadcast error for any candidate with an implausibly large derived radius (regression test added).
*   **Future Work**: train on TESS targets directly (the nightly sync is accumulating exactly that data), recalibrate once there are enough TESS-domain labels, fetch more Kepler stars.

### 8. Real MAST Centroid and Spectroscopy Ingestion -- Now Scheduled; Centroid Estimator Rewritten (2026-10-11)
*   **Description**: `app/pipeline/mast_centroid.py` downloads real TESS 2-minute target-pixel files via `lightkurve`/`astroquery.mast`, computes an aperture-restricted flux-weighted photocentre per cadence, and measures the in-transit shift. `app/pipeline/spectroscopy.py` performs a real VizieR cone-search cross-match against APOGEE-2 DR17 (catalog `III/286`). Both are genuine, non-synthetic measurements (`ExoplanetCandidate.centroid_is_real` / `HostStar.spectroscopy_is_real` distinguish them from `seed_db.py`'s fabricated demo values of the same fields).
*   **Scheduled, no longer a manual script**: `app/pipeline/real_sync.py` (`sync_real_centroids`, `sync_real_spectroscopy`, `sync_real_lightcurve_vetting`) is run by Arq cron jobs in `app/worker.py` (spectroscopy 02:00, centroids 03:00, light-curve vetting 05:00), bounded per night by `CENTROID_SYNC_BATCH` (15), `SPECTROSCOPY_SYNC_BATCH` (100), `LIGHTCURVE_SYNC_BATCH` (10). Every attempt is recorded (`centroid_attempted_at`/`centroid_status`, `spectroscopy_attempted_at`, `lc_vetting_*`), so targets with no TPF / no APOGEE match / no 2-minute light curve are not retried for `SYNC_RETRY_AFTER_DAYS` (90). Downloaded pixel files are deleted after use and only the derived numbers are stored, which is the storage design the earlier "GB-scale" concern asked for. At 15 targets a night the ~7,000-candidate catalog takes over a year to cover for centroids; raise the batch size if the MAST budget allows.
*   **The first centroid estimator was wrong, and its headline result did not survive**: it compared one global in-transit mean with one global out-of-transit mean and divided by a white-noise standard error. TESS centroid series are strongly red (pointing jitter, momentum dumps, slow drift), so that overstated significance. The rewrite uses (1) a per-transit-event local linear baseline, (2) centroids restricted to the SPOC optimal aperture, (3) up to 2 sectors combined, and (4) an **empirical null**: the identical estimator re-run at many fake epochs away from the real transit, so significance is measured against the data's own red noise (unit-tested: calibrated against injected drift + random-walk noise, recovers injected offsets, no false detections beyond the expected rate). The earlier claim that **TOI-104.01 showed a 5.43-sigma / 0.114" centroid offset "worth a human look" is retracted** -- re-measured with the corrected method it is 0.016" at 1.97 sigma (12 events, 2 sectors), i.e. nothing.
*   **Why the raw shift is not the quantity to threshold**: a photocentre shift scales with transit depth (a source at separation d that supplies the whole dip moves the photocentre by ~ d x depth), so even a genuine background eclipsing binary shifts the photocentre by only milli-arcseconds, and so does an on-target transit with a faint neighbour. Re-measuring five real targets (TOI-101.01/102.01/103.01/104.01/105.01) gave shifts of 2.5-16 milli-arcseconds -- one (TOI-101.01) statistically significant at 5.1 sigma and entirely benign. The pipeline therefore also measures the transit depth from the same aperture and reports the **implied source offset** (shift / depth, in arcsec; `centroid_implied_offset_arcsec`), and sets `has_centroid_dip` only if that is both >= 3 sigma and >= 2" (`MIN_IMPLIED_OFFSET_ARCSEC`). **None of the five targets is flagged.** The 2" floor is a conservative engineering choice, not tuned on labelled data -- there is no labelled set of confirmed background-EB centroid cases in this project yet.
*   **Fixed along the way**: for long transits (e.g. 5.6 h on a 4.1 d period) the null-trial guard left no phase space and the function silently returned "not measured" (regression test added).
*   **Where it reaches the user**: `GET /api/v1/candidates/{toi_id}` now has a `real_observations` block (centroid: shift, significance, implied offset and uncertainty, `is_dip`, sector, timestamp; light-curve vetting: class probabilities, sectors, model version). Unmeasured fields are `null`, never zero. `tiers.py` uses the real light-curve flag, so Tier 2/3 are reachable for candidates the nightly sync has processed.
*   **Fixes from an independent code review (2026-10-11)**: (1) a host marked `spectroscopy_is_real` could still carry `seed_db.py`'s fabricated `rad_spec`/`teff_spec`/`alpha_fe` -- a match now overwrites or clears every spectroscopy field; (2) the tabular model no longer substitutes APOGEE Teff/radius for Gaia values (it is trained on Gaia values, so substitution shifted `teff_diff`/`rad_diff` away from the training distribution); (3) one failing target no longer aborts the nightly batch or stalls it by rolling back its own attempt timestamp -- each target is isolated; (4) network/archive failures are recorded as status `error` and retried after 1 day instead of being treated as "no data" and shelved for 90 days (`TransientCatalogError`); (5) the epoch fallback query is filtered to the planet being analysed; (6) a centroid whose depth could not be measured is stored as `has_centroid_dip = NULL` (unknown), not False (clean); (7) the cached study table is invalidated when the feature code changes. (8) the three nightly jobs now take one token per target from the same Redis rate limiter ingestion uses, so the CDS/MAST/NASA budget really is shared (a target's internal MAST downloads still count as one token); (9) `/transit_pipeline` no longer reports `dl_centroid_available` (it implied the classifier used the centroid); it returns `centroid_measured`, and the UI says the centroid check is reported separately.
*   **Spectroscopy**: `spectroscopy_subset_report.json` has the last manual run; APOGEE-2 is a targeted, not all-sky, survey, so a low match rate is the correct outcome.
*   **Caveat**: the Kepler-trained light-curve vetter does not use the centroid (see item 7); centroid evidence is reported alongside it, not fused into it. The per-cadence folded offsets (`centroid_dx_json`/`centroid_dy_json`) are still stored but only the legacy CNN baseline consumed them.
*   **Future Work**: a labelled centroid validation set to tune the implied-offset floor; a difference-image PRF fit (what SPOC DV does) is more sensitive than aperture photocentres for faint neighbours.

## 2. Catalog & API Dependencies

### 1. Schema Dependency on Gaia DR3
*   **Description**: The database schemas, model feature pipelines, and VizieR coordinate queries are hardcoded to the Gaia DR3 column definitions and tables.
*   **Impact**: High fragility to future catalog releases. The upcoming release of **Gaia DR4** (changing table structures and astrophysical parameter pipelines) will break the ingestion pipeline, rendering the automated queries obsolete.
*   **Mitigation**: Limit Gaia query structures to essential astrometric vectors (RA, Dec, parallax, proper motions).
*   **Future Work**: Implement a dynamic catalog abstraction layer that maps incoming features to database structures regardless of release version.

### 2. External API Rate-Limiting -- Mitigated (UPGRADE_PLAN.md D.2)
*   **Description**: The ingestion pipeline makes direct HTTP queries to public astronomy data servers (CDS Strasbourg, VizieR, and MAST).
*   **Status**: A Redis-backed, cross-process token-bucket rate limiter (`backend/app/pipeline/rate_limiter.py`, default 2 requests/second, shared across every Arq worker process via `settings.CATALOG_RATE_LIMIT_PER_SECOND`) is now applied to every NASA TAP GET and every CDS X-Match POST call in `ingest.py`, including retries. This was previously a documented-but-unimplemented risk; it is now real and unit-tested (`tests/test_rate_limiter.py`).
*   **Remaining gap**: The limit is a single global budget, not yet per-catalog (a burst of NASA TAP calls and a burst of CDS calls currently share one bucket) -- acceptable at current scale, worth splitting if catalog count/throughput grows materially (ties to F.5-F.7 adding more catalogs).
*   **Future Work**: Host a local cache database containing TESS and Gaia parameters for flagship sectors to reduce public web query volume further; consider per-catalog buckets if F.5-F.7 catalog volume warrants it.

## 3. Operational & Engineering Limitations

### 1. Standalone Portal Adoption Barrier
*   **Description**: EEFN is designed as a standalone Next.js web application, which requires telescope allocators and schedulers to log into a separate dashboard.
*   **Impact**: Astronomers already suffer from portal fatigue. Standalone deployment prevents actual integration into observer scheduling routines; observers will continue to use ExoFOP and MAST as their single sources of truth.
*   **Mitigation**: Expose all alert flags and ML prediction scores via structured REST API endpoints.
*   **Future Work**: Build integration webhook libraries to export EEFN alert flags directly into ExoFOP-TESS tables.

### 2. Single-Node Database Concurrency -- Mitigated for the primary case (UPGRADE_PLAN.md D.1)
*   **Description**: The backend previously only supported a single local SQLite database file (`eefn.db`), which enforces database-level write locks under concurrent writers.
*   **Status**: Postgres is now a fully supported target (`docker-compose.yml`'s `postgres` service; dialect-agnostic `sqlalchemy.Uuid` columns; Alembic migrations verified against both SQLite and a real Postgres container) -- deploying against Postgres removes the SQLite single-writer constraint. SQLite remains supported for local single-developer use, where the constraint doesn't matter.
*   **Remaining gap**: `DATABASE_URL` must actually be pointed at Postgres for a multi-writer deployment; SQLite is still the default in `app/config.py` for zero-setup local dev, so a deployment that doesn't override this env var would still hit the original limitation.
*   **Future Work**: Document the Postgres `DATABASE_URL` requirement prominently for any non-single-developer deployment (README/deployment guide).

### 3. Idealized Impact Study Assumptions
*   **Description**: The historical impact analysis assumes that ground-based observatories would have allocated expensive observing hours to all false positives blindly.
*   **Impact**: Cost and telescope hours saved are highly idealized and overclaimed. Astronomers manually vet targets using simple filters (e.g., dropping targets with high Gaia RUWE values) before scheduling, meaning actual operational savings are significantly lower.
*   **Mitigation**: Adjust cost-saving statistics to evaluate savings relative to a baseline manual-vetting model rather than a zero-vetting baseline.
*   **Future Work**: Interview observatory scheduling managers to establish realistic baseline allocation strategies.
